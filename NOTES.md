# Инженерные заметки

## Вопросы заказчику и принятые допущения

1. Пересчитывать ли закрытые месяцы после изменения ставки? Принято: нет; API возвращает `skippedInClosedPeriods`.
2. В какой таймзоне считать сутки? Принято: бизнес-дата — `DateOnly`, без timezone; API принимает `YYYY-MM-DD`.
3. Как округлять? Принято: каждую запись half-away-from-zero до копеек, затем суммировать.
4. Что делать с бюджетом 0? Процент и флаги отсутствуют, UI показывает прочерк.
5. Риск и перерасход пересекаются? Принято: риск `(80;100]`, перерасход `>100`.
6. Можно ли переносить запись между месяцами? Да, только если открыты и старый, и новый периоды.
7. Удаление физическое или soft delete? В рамках задания физическое; для бухгалтерского production-контура нужен audit log.
8. В отчёте только проекты с трудозатратами? Да.
9. Итоговый бюджет? Не суммируется: общий процент разных проектов может вводить в заблуждение.
10. Несколько записей сотрудника на один проект/день? Разрешены; дневной лимит считается по всем проектам.

## Ключевые решения

`TimeEntry` хранит `appliedRate` и `amount` как Decimal128. Поэтому месячный отчёт — индексный `$match` + `$group`, без `$lookup` ставки на миллионах строк. Изменение истории ставок пересчитывает открытые записи тем же `Money.Calculate`; закрытые пропускает.

Пересчёт ставок атомарен: сначала пересчитываются все записи в памяти, и только потом история и записи пишутся одной транзакцией (`BulkWrite` в сессии). Раньше история писалась первой, и запрос, упавший на записи без подходящей ставки, оставлял данные пересчитанными наполовину. Каждый `ReplaceOne` фиксирует версию записи, поэтому параллельная правка даёт 409, а не молчаливую перезапись. Для миллионов записей на сотрудника пересчёт нужно выносить в фоновый воркер батчами — см. [SCALING.md](SCALING.md).

Список страницы делает фиксированное число обращений к базе: count, find, totals, справочники по `$in` и одна агрегация дневных часов на всю страницу. До этого дневные часы запрашивались по одному запросу на пару «сотрудник + дата», а справочники читались целиком, — на странице в 50 строк это давало до 55 round-trip.

Дата хранится как UTC midnight, но домен видит только `DateOnly`. Месяц — полуинтервал `[start; nextMonth)`: он корректен на границах и использует индекс, в отличие от `$year/$month`.

Оптимистическая блокировка — поле `version` и atomic replace по `(_id, version)`. Версия обязательна и для удаления: иначе `DELETE` остался бы единственной операцией API, способной пройти мимо контроля конкурентности. Перемещение проверяет закрытость исходного и целевого месяца. ProblemDetails содержит `code`, русский `title`, structured `details` и `traceId`.

## Конкурентность между документами

Лимит 24 часа — правило не про запись, а про сумму записей сотрудника за дату, то есть инвариант поверх нескольких документов. Проверка «прочитали сумму → вставили запись» его не держит: два параллельных запроса читают 8 часов, каждый разрешает себе ещё 10, и день заканчивается на 28. Транзакция Mongo сама по себе тоже не спасает — snapshot isolation конфликтует по одинаковым документам, а не по вставке нового.

Поэтому появилась коллекция `daily_hours`: один документ на пару «сотрудник + дата», по которому проходит каждая запись дня. Резервирование — условный `$inc` с фильтром `totalHours <= 24 - hours`: пока в дне есть место, инкремент применяется; когда места нет, документ не совпадает с фильтром, upsert натыкается на существующий `_id` и даёт duplicate key, который превращается в обычный 409. Две транзакции, одновременно трогающие один и тот же документ дня, дают write conflict, и `WithTransactionAsync` их сериализует, повторяя транзиентную. Запись в `time_entries` и резервирование идут одной транзакцией, поэтому «зарезервировали, но не записали» невозможно.

`daily_hours` — производное состояние: источник истины остаётся `time_entries`, сидирование пересчитывает документы заново, а интеграционный тест сверяет их с агрегацией после серии create/update/move/delete. Проверка лимита в `TimesheetService` никуда не делась: она даёт человеку понятное сообщение с числами, а гарантию обеспечивает уже гейт в хранилище.

Цена: один горячий документ на сотрудника в день. Для табеля это правильный компромисс — сотрудник физически не создаёт сотни записей за один день параллельно.

**Что осознанно не закрыто.** Закрытие периода живёт в том же классе задач: запрос успел прочитать «февраль открыт», бухгалтер закрыл месяц, запрос дописал запись. Строгая гарантия требует, чтобы запись и закрытие конфликтовали на одном документе — то есть month-level anchor, на который контендят вообще все записи месяца. Это заметно хуже по пропускной способности, чем документ на день, а окно гонки — доли секунды между чтением и записью, поэтому в рамках задания оставлено как известное ограничение, а не закрыто наспех.

Переработка — свойство суммы дня, не записи. Итоги списка считаются отдельной серверной агрегацией по полному фильтру, не по странице.

## Индексы

| Индекс | Запрос | Причина порядка |
|---|---|---|
| `time_entries {date, projectId}` | отчёт по месяцу | range даты сокращает набор перед group |
| `time_entries {employeeId, date}` | дневной лимит, сотрудник + месяц | ESR: equality до range |
| `time_entries {projectId, date}` | проект + месяц | ESR: equality до range |
| `projects {code}` unique | шифр проекта | инвариант защищает БД |
| `closed_periods {year, month}` unique | статус месяца | один документ на период |
| `daily_hours {_id}` | гейт дневного лимита | `_id` = «сотрудник + дата», уникальность даёт сам первичный ключ |

Для глубокой пагинации `skip` деградирует линейно. Следующий шаг — cursor/keyset по `(date, _id)`.

Индексы создаются в одном месте (`MongoIndexCatalog`) и вызываются и на старте приложения, и после сидирования. Раньше сидирование дропало коллекции и уносило индексы вместе с ними: после `POST /api/seed` в `time_entries` оставался только `_id_`. Инвариант закреплён тестами `IndexLifecycleTests`, включая проверку `explain` на IXSCAN, и вынесен в отдельный шаг CI.

## Frontend state

React Query отвечает за server-state, дедупликацию и invalidation. Formik + Yup выбраны в соответствии со стеком команды. Zustand установлен как допустимый контур локального UI-state; текущие два переключателя проще оставить локальными — глобальный store здесь был бы лишним.

Экран разделён на `features/entries`, `features/report`, общие `components/` и форматтеры в `lib/`: раньше весь интерфейс жил в одном файле на 523 строки. Пагинация держит предыдущую страницу на экране, пока грузится следующая (`keepPreviousData`), иначе счётчик записей на миг обнулялся. Удаление записи спрашивает подтверждение и отправляет версию строки; после удаления последней строки страницы список отступает на страницу назад — это делает обработчик события, а не эффект.

Анимации оформлены как декорация: ни один экран не зависит от того, доиграла ли анимация, а `prefers-reduced-motion: reduce` отключает их целиком. Брейкпоинты — 375 / 480 / 768 / 1000 / 1280 / 1440 / 1680 / 1920.

## Производительность

Отчёт не materialize-ит записи в C#: группировка выполняется MongoDB. Перед production необходимо прогнать миллионный seed, сохранить `explain('executionStats')` и подтвердить `IXSCAN`. Числа производительности не выдуманы: в документ не внесены измерения, пока они не выполнены на стабильном окружении.

## Осознанно не сделано

- Аутентификация, роли, Kubernetes и микросервисы исключены самим заданием.
- SignalR не добавлен: корректность и тестируемость важнее live-refresh.
- Сериализация записи с закрытием периода: нужен month-level anchor, на котором контендят все записи месяца. Описано выше, сделано осознанно не было.
- Нет предагрегированных rollup: текущий индексный отчёт соответствует объёму задания.

## Гейты

CI выстроен цепочками, чтобы красный прогон показывал стадию, а не лейбл «backend упал»:
frontend — install → format → lint → typecheck → test → build; backend — restore → format →
build → unit → integration → index lifecycle; отдельно semgrep и проверка языка комментариев.
Последняя запрещает кириллицу в комментариях, но не трогает строки: пользовательские
сообщения остаются русскими, этого требует задание.

## При удвоенном времени

Hangfire-пересчёт ставок батчами; monthly rollup через change streams; snapshot отчёта при закрытии; audit log и soft delete; keyset pagination; транзакционный guard дневных часов; k6-профиль и explain regression test на миллионе записей.
